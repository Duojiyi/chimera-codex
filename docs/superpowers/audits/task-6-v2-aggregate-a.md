## Method

Read the Task 6 section of the Plan (`docs/superpowers/plans/2026-07-26-chimera-plus-v2-rearchitecture.md:127-137`), §10 of the Spec, ADR-008 and ADR-009, and the TODO's D6 change record (`2026-07-26-chimera-plus-v2-rearchitecture-todo.md:108-124`) before judging anything, per the note that D6 voided the original Step 6.2 MSIX-inclusion clause. Then read every file in scope end-to-end, traced call graphs with `grep`/`ToolSearch`-equivalent search across the whole repo (not just the listed files) to find *callers*, not just definitions, ran the real test suites, and did two live break/restore experiments (digest check, bundle-contract self-test) to confirm the protections are real rather than vacuous.

All green on a clean run. One transient run showed 2-4 unrelated failures in `step6_3_download.rs`; re-running immediately after showed 15/15 passing five times in a row, and a `git status` at that moment revealed a concurrent, uncommitted mutation to `download.rs` (`if false && written > spec.size_bytes`) from another live session — not something I introduced. ## Step-by-step findings

### Step 6.1 — bill of materials, version naming, minimum disk space, user-writable directory, WebView2 preflight; ADR chooses licensed Evergreen Standalone or fixed-runtime approach

**Status: MET**

- ADR-009 (`docs/architecture/decisions/ADR-009-webview2-and-bill-of-materials.md`) documents the BOM (`Chimera++.exe`, `NOTICE`, `LICENSE`, `checksums.txt`), version-naming scheme matched by `v2-release-manifest.mjs`, and resource requirements (~60 MB install, 2× payload free space at first run, per-user `%LOCALAPPDATA%` install).
- The Plan's literal wording asks the ADR to pick between "Evergreen Standalone" or "fixed runtime". ADR-009 instead picks a third option — redistribute neither, preflight + redirect to Microsoft — with an explicit, reasoned rejection of both named options (unsigned-installer trust chain, unowned browser-engine CVEs, size). This is exactly the kind of deliberate, ADR-documented deviation the TODO's change record treats as valid for D6, and the TODO's own R10 entry confirms it was accepted product-owner-side ("按 ADR-009 取消"). I judge this MET on the process requirement (an ADR decided the strategy with real trade-off analysis), not a gap.
- `crates/chimera-platform/src/webview2.rs:85-98` (`check_webview2`) checks HKLM then HKCU, treats empty/all-zero versions as `Missing` (tombstone handling), `webview2.rs:65-67` sends the user to Microsoft's own URL. `crates/chimera-platform/tests/webview2_preflight.rs` — 9 tests, all passing, cover machine-wide, per-user, empty-string, all-zeros, and asserts `download_url()` is `https://` and points at `microsoft.com`.
- Wired into the app: `bootstrap_cmds.rs:71-75` calls `webview2::check_installed()` inside `run_preflight`, which is invoked from `FirstRun.tsx:49` before `App.tsx` ever renders the main UI (`App.tsx:43-60` — `ready` gates the whole tree). This ordering guarantee (preflight before any state write) is real: `AppState::initialise()` (`state.rs:109-138`) is called once at process start and only creates the Chimera data directory (never touches Codex config or the runtime), and `run_preflight` itself performs no destructive writes — `download::preflight`'s write-probe (`download.rs:122-132`) creates and immediately deletes a marker file, which is the correct way to test writability with a real write (catches ACL/read-only-mount cases a metadata check would miss) without leaving state behind.
- Minimum disk space: `UNPACK_HEADROOM = 2` (`download.rs:34`) matches ADR-009's documented "2× the payload size" and is tested (`preflight_demands_headroom_beyond_the_payload_itself`).

### Step 6.2 — installer must not contain any official Codex binary, Key, or token; must contain a reference to the signed stable manifest, checksums, and NOTICE; bundle-contract gate with a self-proof that stuffing a payload in turns it red

**Status: MET, with one minor gap**

- `scripts/test-bundle-contract.mjs:44-68` matches `codex.exe`, bare `codex`, `chatgpt.exe`, `codex.app` (case-insensitive basename) and `.msix/.msixbundle/.appx/.appxbundle` extensions anywhere in the tree, plus six secret patterns (OpenAI-style key, GitHub PAT/fine-grained token, AWS key id, JWT, credentialed URL, PEM private key).
- Self-proof exists and is real: `REJECTION_CASES` (`test-bundle-contract.mjs:148-180`) synthesizes a bundle with `payload/Codex.exe`, a nested `.msix`, a `resources/bin/codex`, an embedded fake key, a credentialed URL, a PEM header, and a bundle missing `NOTICE`, and asserts each is rejected. I independently broke the payload-name rule (`if (false && FORBIDDEN_PAYLOAD.some(...))`) and reran: `self-test: rejects a bundled Codex.exe` and `rejects a Codex binary nested in a subdirectory` both flipped to `✗`, confirming the gate is load-bearing rather than a rule nobody exercises. Restored immediately; `node scripts/test-bundle-contract.mjs` now passes clean and `git status --short scripts/test-bundle-contract.mjs` is empty.
- `.github/workflows/v2-release.yml:124,192` runs the gate against the actual built NSIS/DMG tree (`--dist`), not just the structural self-test, and `v2-release.yml:199-207` additionally scans the *release workflow's own recipe* for a payload-fetch step, so a payload creeping back in at build time is caught even before an artifact exists.
- Gap: `REQUIRED_FILES = ["NOTICE", "LICENSE"]` (`test-bundle-contract.mjs:71`) does **not** include `checksums.txt`, even though ADR-009's BOM and Step 6.2's own text both name it as required. Today's CI (`v2-release.yml:117-119,187-189`) does generate it, so the artifact that would actually ship has it — but the automated gate that is supposed to be the single enforced source of truth for "what must ship" would not notice if that `sha256sum * > checksums.txt` line were ever dropped from the workflow. This is a real, minor gap in the gate's completeness, not a shipped-artifact defect today.
- "Reference to the signed stable manifest": no such reference exists anywhere in the client or the bundle — see Step 6.3, where I show nothing in the shipped code ever consumes a stable manifest at all. There is nothing to point at yet, and the bundle-contract gate is not what was supposed to enforce this clause in any case (it enforces *absence* of a payload, not *presence* of a manifest pointer).

### Step 6.3 — first-run preflight, on-demand download, digest **and signature** verification, managed install, repeatable launch; disconnection/interruption/disk-full recovered by Task 5's transaction journal, with fault-injection tests (R7)

**Status: NOT MET.** This is the load-bearing step of the whole Task, and the two properties that matter most — a real download *trigger* and a real *managed install* — do not exist as reachable code. What exists are two well-tested but mutually disconnected pieces.

**What is real and well-built, in isolation:**
- `crates/chimera-runtime/src/download.rs`: `fetch_payload` streams to a `.part` file, checks size mid-stream (not just at the end — `download.rs:209`) and re-checks on truncation (`download.rs:221`), verifies SHA-256 only after `sync_all()` (`download.rs:228-238`), and only then atomically renames into place. `redirect_allowed` (`download.rs:266-268`) refuses a cross-origin redirect. 15 tests in `crates/chimera-runtime/tests/step6_3_download.rs` cover the happy path, wrong digest, size lies (both over- and under-declared), a mid-stream connection drop, total unreachability, retry-after-failure, and that error text leaks neither the mirror URL nor raw `io::Error` text.
- **I broke the digest check directly** (`if !actual.eq_ignore_ascii_case(...)` → `if false && ...`) and reran `a_wrong_digest_is_refused_and_discarded` in isolation: it failed (`called Result::unwrap_err() on an Ok value`), confirming the check is real, not vacuous. Restored; reran; passes; `git status --short` on the file is empty.
- `crates/chimera-runtime/src/update.rs`: `stage_version`/`commit_version` implement an atomic, journal-backed version swap with a lock (Task 5's machinery), independently tested in `step5_3_update.rs`, `step5_4_transaction.rs`.

**What does not exist — verified by exhaustive call-graph search, not inference:**
- `fetch_codex_payload` (`bootstrap_cmds.rs:113`, registered at `lib.rs:60`) is a Tauri command that takes `version, url, size_bytes, sha256` **as raw arguments from whoever calls it** and downloads+digest-checks them. I grepped the entire repository for `fetch_codex_payload` outside its own definition and registration: zero hits. `FirstRun.tsx` — the only first-run screen that exists — calls `run_preflight` and, on success, calls `onReady()` directly (`FirstRun.tsx:60`); it never calls `fetch_codex_payload`. No other frontend file, no `setup()` hook in `lib.rs`, and no test harness calls it either. The command is dead code from the running application's point of view.
- Nothing in the shipped code ever fetches or verifies a *signed stable manifest* for the Codex payload. `chimera-runtime::download` takes `sha256`/`url`/`size_bytes` as given, trusting that "the caller" sourced them from a verified manifest (stated explicitly in the module's own doc comment, `download.rs:9-12`) — but grep for `mirror-contract`, `MirrorClient`, `StableManifest`, a mirror URL constant, or a mirror public key anywhere in `chimera-runtime` or `apps/chimera-desktop/src-tauri` returns nothing except that one doc comment. `crates/chimera-update` implements a full TUF-style root→timestamp→snapshot→targets verification chain (`trust.rs`) that could in principle serve this role, but it is not even a Cargo dependency of `apps/chimera-desktop/src-tauri` (`grep chimera-update apps/chimera-desktop/src-tauri/Cargo.toml` — no hits). There is no client-side signature verification of *anything* that determines what digest gets passed to `fetch_payload`.
- "Managed install" (unpack the verified payload into `stage_version`'s directory, call `commit_version`) does not exist. I grepped every call site of `stage_version(` and `commit_version(` in the repository: every single one is inside `crates/chimera-runtime/tests/*.rs`. Zero production callers.
- Consequently, `runtime_cmds.rs:179-184` (`apply_codex_update`) is hard-coded: `Err("Updating is not enabled in this build. The verified download and staged commit are not wired yet.")`. `repair_runtime` (`runtime_cmds.rs:123-134`) likewise always errors: `"No managed runtime to repair. Install Codex first — managed install is not enabled in this build."` `get_runtime_status` hard-codes `update_available: false` (`runtime_cmds.rs:79`) so the one UI affordance that could reach `apply_codex_update` (`codex/index.tsx:222,259-278`) never even renders in production. `launch_codex`'s only failure message for "nothing installed" (`commands.rs:323-325`) is "Open the Codex tab to prepare the managed runtime" — but the Codex tab's only action for that state (`repair_runtime`) is the hard-coded refusal above. **There is no path — automatic or manual — through the shipped UI by which a user ever obtains a working Codex install.** Even a test in the codebase names this directly: `bootstrap_cmds.rs`'s own unit test is called `an_unused_payload_spec_still_compiles_against_the_runtime_contract` (`bootstrap_cmds.rs:171-182`) — "unused" is the author's own word for it.
- Fault injection for the *download* sub-problem (network loss, mid-transfer drop, size lies) is genuinely present and good (the 15 tests above). Fault injection for the *install* sub-problem (interrupted unpack, interrupted commit) exists only in Task 5's own suite, exercising `stage_version`/`commit_version` directly with hand-placed files — it has never been exercised with a real downloaded-and-verified payload because no code produces one.

Because the two headline properties Step 6.3 asks for — "按需下载" (on-demand download, i.e. something triggers it) and "managed install" — are both entirely absent as reachable code, and because the step's own two named sub-requirements ("digest **与签名校验**") are only half-present (digest yes, signature no), I am not marking this PARTIAL. The pieces that exist are solid, but the step as a whole delivers zero end-to-end capability: a fresh install on a perfect machine (network up, WebView2 present, disk space available) can never get Codex running through anything the app ships.

### Step 6.4 — customer-visible portable limitations and cleanup entry point; no fake MSIX identity, protocol, or uninstall entry

**Status: MET**

- `crates/chimera-runtime/src/portable.rs:54-62` (`limitations()`) lists exactly the five items the Spec names (no package identity, no Store updates, no `codex://` registration, no file associations, no Apps & Features entry), each with an i18n key (`detail_key()`), not a bare flag. `uninstall_registration()` (`portable.rs:70-72`) hard-returns `false`.
- `cleanup_plan`/`CleanupPlan::execute` (`portable.rs:123-190`) is a genuine describe-then-execute two-step: `get_cleanup_plan` (`portable_cmds.rs:63-78`) only reads; `execute_cleanup` (`portable_cmds.rs:85-90`) **re-derives the plan from `state.paths` rather than accepting one from the frontend** — this closes off the obvious attack of a plan crossing the IPC boundary and coming back naming an arbitrary path.
- 10 tests in `step6_4_portable.rs` cover: all five limitations disclosed, each has a non-trivial key, no Apps & Features registration, plan built before delete, keychain-entries flag set, plan never reaches outside the two given roots (tested by planting a sibling directory and asserting it's untouched), idempotent double-execute, execute leaves outsider files alone, and labels never contain a path separator (screenshot-safety). All pass.
- `dir_size` (`portable.rs:99-115`) explicitly does not follow symlinks out of the tree and does not count them, matching "cleanup does not reach outside the two roots it was given."

## Stop-condition verification

| Stop condition | Verdict | Evidence |
|---|---|---|
| Downloaded payload not accepted unless it matches an approved digest | **MET** at the crate level, **unverifiable end-to-end** | `download.rs:233-238` rejects on mismatch; broken and confirmed red, then restored (see Step 6.3). But since nothing ever calls `fetch_payload` with manifest-sourced data in production, "approved" has no operational meaning today — the digest is just whatever the (nonexistent) caller passes in. |
| Installer contains no official Codex binary and no secret | **MET** | `test-bundle-contract.mjs`; self-tests broken and confirmed red for the payload-name rule, then restored (see Step 6.2). Runs against the real built artifact in CI, not just synthetic fixtures. |
| Provenance mismatch is refused | **PARTIAL, mostly NOT MET** | Origin-pinning on redirects is real and tested (`redirect_allowed`/`the_http_source_refuses_an_off_origin_redirect`) — a mirror cannot bounce the request to a different host than the manifest named. But "provenance" in the Spec's sense (a signed stable manifest vouching that a digest is the *approved* one) has no client-side consumer at all — no code fetches a manifest, no code verifies its ed25519 signature, no public key or mirror URL is embedded anywhere in the client. A forged or stale digest fed to `fetch_codex_payload` would be accepted exactly as readily as a correct one, because nothing checks where it came from. |
| Interrupted download leaves nothing partial | **MET** | `.part`-then-rename with cleanup on every error path (`fetch_payload`, `download.rs:163-183`); tested by `a_dropped_connection_leaves_no_partial_file` and `a_failed_download_can_simply_be_retried`. |
| Running from a read-only directory does not corrupt state | **MET** | All Chimera state lives under `%LOCALAPPDATA%\ChimeraPlusPlus` (`state.rs:28-37`), never beside the executable, so the executable's own directory being read-only (the ZIP/portable case) is irrelevant. If the data root itself cannot be created, `AppState::initialise()` fails loudly and the process exits (`lib.rs:24-29`) rather than partially writing anything. `download::preflight`'s `NotWritable` path (write-probe) additionally refuses to start a download into an unwritable runtime root, tested by `preflight_refuses_an_unwritable_runtime_root`. |

## What I verified by breaking, and what happened

1. **Digest check** (`download.rs`): disabled the SHA-256 comparison → `a_wrong_digest_is_refused_and_discarded` failed with the wrong-digest payload accepted and left on disk. Restored; test green again; `git status` clean on the file.
2. **Bundle-contract forbidden-payload rule** (`test-bundle-contract.mjs`): disabled the `FORBIDDEN_PAYLOAD` basename check → 2 of the gate's own self-tests (`rejects a bundled Codex.exe`, `rejects a Codex binary nested in a subdirectory`) flipped from ✓ to ✗, and the script's own exit code went from 0 to 1. Restored; back to `PASS`; `git status` clean on the file.

Both protections are real, not decorative.

## What I could not verify, and why

- **Step 6.5 in its entirety** (clean Windows VM, no-admin first run, first-run download, offline degradation, online update, corrupted-payload rejection) requires a real Windows VM and a real reachable Codex mirror serving a real signed manifest — neither exists in this environment (this machine *is* Windows, but there is no mirror deployment, no `CHIMERA_APP_SIGNING_KEY`/mirror key pair provisioned, and — per the Step 6.3 finding above — no code exists yet that would even attempt the download during a real run). This is consistent with the TODO's own admission that T46 is "代码完成，缺干净 VM 实测", except that what I found is not merely "untested," it is "the code path under test does not exist."
- **A real NSIS build scanned end-to-end.** I verified the bundle-contract gate structurally and via its self-tests, and read the CI job that runs it against a real `--dist` tree, but did not run a full Tauri/NSIS build in this session (out of scope for a source-reading audit, and not something I could meaningfully add to without the full Windows build toolchain and code-signing environment already excluded by ADR-008).
- **A real signed mirror manifest.** `services/mirror-contract`'s signature/CAS code is Task 4's scope, and whether *that* side is complete is not something I re-verified here — Task 6's job was to consume it, and it doesn't.

## Verdict

**FAIL.**

Steps 6.1, 6.2, and 6.4 are genuinely well-built and I confirmed their protections are load-bearing by breaking and restoring them. But Step 6.3 — the step that is the entire reason D6 exists ("client downloads and verifies the payload on first run, same as Codex App Manager") — has no working implementation. The download function and the managed-install function both exist and are individually well-tested, but nothing in the shipped application calls either of them, there is no client-side signature verification of any manifest, and every UI action that would let a user obtain a working Codex install is hard-coded to refuse with "not enabled in this build." A user who runs Chimera++ today, on a machine with network access, WebView2, and free disk space, reaches the main UI and has no way — automatic or manual — to ever get Codex running. That is not a clean-VM evidence gap; it is a missing acceptance criterion (Step 6.3: "实现首启 preflight、按需下载...managed install 和可重复启动"), and Auto Mode does not make it retroactively true. T46 should not be checked off on this evidence.
