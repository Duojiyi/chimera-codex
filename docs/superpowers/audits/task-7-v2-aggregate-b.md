# Task 7 (T47) Audit B — Architecture & Failure Boundaries (v2)

**Date:** 2026-07-26
**Scope:** Steps 7.1–7.4. `crates/chimera-migration/` (all), `apps/chimera-desktop/src-tauri/src/migration_cmds.rs`.
**Auditor:** Independent B — architecture and failure boundaries only; no Spec-coverage checklist, no reliance on commit messages or doc comments.
**Repo state:** started this audit at `86ca8fe`; the repo is live and moved forward twice during the audit (`3881f82`, then `6d854d0`) as another agent landed a migration-panel frontend. Findings below are checked against final HEAD `6d854d0`. No file this audit changed is left modified — see "What was verified by breaking" for the temporary edits/tests made and reverted, and the note on `git status` at the end.

## Verdict

**FAIL** — Stop condition "two managers cannot concurrently write the same target" is not enforced anywhere in the executable path. The Step 7.4 coexistence module is real, well-tested, and inert: nothing in the desktop shell ever calls it, and the one write path this task adds (`run_migration`) takes no lock at all, unlike every other state-changing command in this codebase. This is compounded by a demonstrated, reproducible bug: `apply_migration`'s rollback overwrites live config with a stale snapshot with no re-check of what is actually on disk now, silently destroying a concurrent legitimate write. Four of five stop conditions independently hold; this one does not, and it is the condition Step 7.4 exists to satisfy.

## Method

Read every file in scope end to end, not just the diff. Ran the crate's real test suite, then attacked five things by actually trying to defeat them: (1) added a throwaway reproduction test that exercises the exact "someone else writes config.toml while migration is in flight" interleaving through the real `ConfigSnapshotPort` contract; (2) tried to construct `OwnershipTakeoverConfirmation` from outside its module to see if the confirmation gate is real or cosmetic; (3) deleted the HTTPS-only URL check in `migrate.rs` to confirm the regression test it protects actually goes red; (4) cross-checked every doc-comment claim about 1.x file layout against the real `codex-plus-core` source rather than trusting it; (5) grepped the entire repo (not just the migration crate) for any real wiring of `CoexistencePort` or `OperationLock` into the migration write path. All temporary edits were reverted; `cargo test -p chimera-migration --locked` passes (38/38) at the end exactly as at the start.

## Stop-condition findings

### 1. Source database and 1.x files are never written — PASS

`legacy_source.rs` and `ccswitch_source.rs` only ever call `std::fs::read_to_string`/`read` on the source paths; there is no `fs::write`, `File::create`, or `OpenOptions` touching `settings_path` or `config_path` anywhere in either module. The guarantee is also structural, not just careful coding: `MigrationCandidate` (`migrate.rs:48-61`) and `LegacyProviderCandidate`/`CcSwitchProviderCandidate` carry no path or file handle — by the time a candidate exists, there is nothing left in it that could be used to write back to the source even by a future refactor. `read_legacy_inventory`/`read_ccswitch_inventory` fail closed on unrecognized shapes rather than guessing (`LegacyReadError::Corrupt`, `CcSwitchReadError::UnknownSchema`).

Verified real, not just asserted: `read_only_source_legacy_settings_file_is_never_modified_by_a_failed_migration` and `read_only_source_ccswitch_config_is_never_modified_by_a_successful_migration` (`tests/step7_3_migrate.rs:562-639`) write a real file to a tempdir, run the full transaction to completion (one on the failure path, one on the success path), and diff the bytes before/after. Both pass. `codex-plus-core/src/paths.rs:6-7` confirms `APP_STATE_DIR = ".codex-session-delete"` and `SETTINGS_FILE = "settings.json"` match `legacy_source.rs:168-169` exactly — this specific doc-comment claim is true, unlike some others flagged elsewhere in this codebase.

Windows-specific fault injection is real, not aspirational: `a_file_exclusively_locked_by_another_handle_is_reported_as_source_unavailable` (`tests/step7_2_ccswitch_import.rs:301-329`) opens the CC Switch config with `share_mode(0)` and confirms the reader gets `SourceUnavailable` rather than hanging or panicking. Ran it on this machine — passes.

### 2. A failed migration leaves live config byte-identical — PASS in isolation, FAILS under any concurrent writer

The crate's own round trip is correct and well tested: `apply_migration` snapshots first (`migrate.rs:211-213`, before any write), and `roll_back_and_report` (`migrate.rs:422-456`) restores that exact snapshot on any failure, unwinding keychain/DB writes in reverse. `a_keychain_write_failure_leaves_live_config_byte_identical_to_before` and `a_health_check_failure_rolls_back_every_provider_and_secret_migrated_this_run` (`tests/step7_3_migrate.rs:353-454`) both assert byte-for-byte equality after failure, and both pass.

But the restore is unconditional — there is no re-read/hash-compare of the live file before overwriting it with the snapshot. Compare this to `chimera-provider`'s `SwitchTransaction`, which does this correctly for the same `config.toml`: acquires `OperationLock` (`crates/chimera-provider/src/transaction.rs:120-122`), then re-reads and hashes the live file immediately before committing (`transaction.rs:159-161`, the CAS step Spec §7.4 mandates), refusing to overwrite if something else changed it. `chimera-migration::migrate::apply_migration` has neither the lock nor the re-read. It has a `pre_migration_snapshot`, and it writes that snapshot back on failure, unconditionally, regardless of what is on disk *now*.

**Verified by reproduction** (temporary test, removed after use — `crates/chimera-migration/tests/zzz_auditor_b_repro.rs`, built on the exact same `ConfigSnapshotPort` shape as `migration_cmds.rs::RealConfig`): wrote `PRE-MIGRATION-CONFIG` to a real file, ran `apply_migration` with two candidates where the first candidate's `ProviderSink::insert` succeeds and, as a side effect standing in for a genuinely concurrent writer (a second `switch_provider` call, another Chimera window, an external manager, or the user's own edit), writes `CONCURRENT-EXTERNAL-WRITE-AFTER-SNAPSHOT` to that same file; the second candidate then fails, forcing rollback. Result: the file ends up as `PRE-MIGRATION-CONFIG` — the concurrent writer's change is gone, with zero conflict detection, zero warning, zero trace. Ran it: `cargo test -p chimera-migration --test zzz_auditor_b_repro -- --nocapture` → `CONFIRMED: rollback overwrote the concurrent writer's change with the stale snapshot, with zero conflict detection and zero warning.` (test passed, i.e. the bug is confirmed present). This is exactly the failure mode Spec §7.4 names and requires a guard against ("若...其他进程在 snapshot 后改过文件，事务进入显式冲突状态并保留 candidate/snapshot，不得覆盖外部新内容") and `chimera-provider` already implements correctly elsewhere in this same codebase.

This is not a theoretical concern specific to a contrived double: since neither `run_migration` nor `apply_migration` takes any lock (finding 4 below), the exact interleaving above — a `switch_provider` call landing on `config.toml` while a migration is mid-flight and later fails for an unrelated reason (bad key, DB error, health check) — is reachable today with two ordinary user actions in two windows, no adversary required. The new frontend's confirm-dialog copy (`migration.confirm`, added in `6d854d0`) tells the user "any failure restores it exactly" — true only so long as nothing else touched `config.toml` in the interim; the reproduction shows what "exactly" actually means when that assumption breaks.

`restore_pre_migration_configuration` (the separate, explicit "undo a successful migration" entry point, `migrate.rs:403-410`) has the identical gap — it calls `config.restore(snapshot)` with no freshness check either — though this one is at least an explicit, deliberate user action rather than an automatic failure-path side effect, and it is not currently wired to any Tauri command at all (see finding 4), so it is unreachable in the shipped app today.

### 3. 1.x advanced features (N1–N6) are not migrated — PASS, with a wiring gap in the transparency this stop condition also implies

Structurally guaranteed, not just filtered: `LegacyProviderCandidate` and `CcSwitchProviderCandidate` (`legacy_source.rs:121-129`, `ccswitch_source.rs:42-50`) hold only `source_id`/`display_name`/`base_url`/`protocol`/`is_active or is_current`/a redacted key — there is no field for MCP/skills config, user scripts, watcher state, or session data to occupy even by accident. `dropped_feature_sections_are_detected_but_their_payloads_never_reach_output` (`tests/step7_1_legacy_inventory.rs:340-400`) plants a sentinel string inside every dropped section and asserts it never appears in the provider fields or in `{inventory:?}` — passes.

Gap: the auxiliary-marker detection for three of the six dropped-feature categories (user scripts, watcher, session database — `DroppedFeature::UserScripts`/`Watcher`/`SessionDatabase`) depends entirely on caller-supplied paths via `LegacyAuxiliaryMarkers` (`legacy_source.rs:59-64`), which the crate correctly never resolves itself so tests stay hermetic. But `migration_cmds.rs::collect_candidates` (`migration_cmds.rs:237-239`) constructs `LegacySourcePaths::new(...)` and never calls `.with_auxiliary(...)` — so in the actual shipped app, `LegacyAuxiliaryMarkers::default()` (all `None`/empty) is what always gets used, and `detect_auxiliary_dropped_features` (`legacy_source.rs:281-299`) can never fire, regardless of whether the user's real 1.x install has user scripts, a watcher flag, or a session database. The real paths exist and are resolvable — `codex-plus-core/src/watcher.rs:33` (`default_watcher_disabled_flag`), `codex-plus-core/src/user_scripts.rs` (`config_path`), `codex-plus-core/src/codex_sqlite.rs:11-50` (session/thread-reference/log DB paths) — they are simply never passed through. Nothing gets migrated either way (that guarantee holds independent of this), but the user-facing disclosure this task's own design explicitly cares about ("shown so a user learns what they are losing before they migrate rather than discovering it afterwards" — `migration_cmds.rs:56`) silently under-reports for exactly the three categories that carry the most 1.x-specific weight.

Minor, separate note: the `DroppedFeature` doc comments (`legacy_source.rs:81-93`) label `UserScripts` as "N4" and `Watcher` as "N6". Per the TODO's actual N1–N6 (`docs/.../2026-07-26-chimera-plus-v2-rearchitecture-todo.md:75-80`), user scripts are part of N3 and Watcher is part of N4 — the code's cross-references are swapped relative to the TODO's numbering. Behavior is unaffected (nothing is migrated in any case); flagged only because the task brief specifically asked not to trust doc comments at face value.

### 4. Two managers cannot concurrently write the same target — FAIL

This is the primary finding. Two independent things are both true:

**(a) `run_migration` takes no lock at all.** `apps/chimera-desktop/src-tauri/src/migration_cmds.rs:290-329` calls `apply_migration` directly against the real keychain, the real provider DB, and the real `config.toml`, with no `OperationLock` acquisition anywhere in the file (confirmed by grep across the whole file — zero matches for `OperationLock`/`operation_lock`). Compare `commands.rs:172-241` (`switch_provider`, via `SwitchTransaction::new(..., state.paths.operation_lock(), ...)`) and `commands.rs:251-254` (`restore_official`, `OperationLock::new(state.paths.operation_lock())`) — both take the same cross-process file lock at `Paths::operation_lock()` (`state.rs:71-73`) before touching `config.toml`. `run_migration` is the only state-changing command in this codebase's Tauri layer that writes to a domain another command also writes to (`config.toml`, via its snapshot/restore path; the provider DB directly) without taking that lock. There is no single-instance guard either (`lib.rs` has no `tauri-plugin-single-instance`, confirmed by grep), and Tauri commands run concurrently by default, so a `switch_provider` call and a `run_migration` call from the *same* running app can genuinely interleave on separate threads, not just across two OS processes.

**(b) The module built to satisfy this exact stop condition has no live implementation and no command surface.** `coexistence.rs` defines `CoexistencePort`, `detect_coexistence`, and `take_ownership` correctly and the crate's own tests (`tests/step7_4_coexistence.rs`, 18/18 passing) exercise every branch with an in-memory `SpyProbe`. But grepping the *entire* repository (not just the migration crate) for `impl CoexistencePort` or any real filesystem-lock/process-list backing finds nothing outside `coexistence.rs` itself and its own test file. `migration_cmds.rs`'s own module doc comment claims "Migration from Chimera++ 1.x and CC Switch, and coexistence detection" (line 1) — the coexistence half of that sentence is not true of this file: `detect_coexistence` and `take_ownership` are never called anywhere in it, or anywhere else in `apps/chimera-desktop`. `lib.rs`'s `generate_handler!` registers exactly two migration commands (`preview_migration`, `run_migration`) and nothing coexistence-related. The frontend (`apps/chimera-desktop/src/features/settings/index.tsx`, including the migration panel newly landed at HEAD `6d854d0`) has zero coexistence-related strings, components, or `invoke()` calls — confirmed by grep across `src/i18n/en.ts`, `src/i18n/zh.ts`, and the panel component itself; the only "ownership" string in the whole app (`codex.ownershipVerified`) belongs to Task 5's runtime-ownership display, not this task's coexistence conflict detection.

Net effect: as shipped, running Chimera alongside CC Switch, a legacy Chimera 1.x install, or Codex App Manager triggers **no detection, no read-only fallback, no conflict banner** — the Spec §12.3 requirement ("Chimera 启动时检测已知 operation lock、ownership 和进程；发现其他管理器活动操作时进入只读状态") has a correct, tested implementation sitting in the crate with literally nothing calling it. This is not "the UI for a working feature is missing" (which the instructions say not to penalize) — it is "the write path is live and reachable, and the specific safety mechanism this task exists to build for that write path is disconnected from it end to end." The TODO's own status line for T47 ("代码完成，缺 UI 与共存实机矩阵" — code complete, missing UI and a real-machine coexistence matrix) undersells this: the gap is not only UI/real-machine evidence, it is that the backend integration point for coexistence protection does not exist anywhere in the desktop shell, and the one migration write command that does exist skips the lock every comparable command in this codebase takes.

One thing that *does* incidentally limit the damage: `providers` table has `id TEXT NOT NULL PRIMARY KEY` (`crates/chimera-provider/src/db.rs:53-54`), and provider ids are deterministic (`deterministic_provider_id`, `migrate.rs:136-139`), so two literally-simultaneous `run_migration` calls racing to insert the same provider will have one insert fail on the SQLite constraint rather than silently duplicate — that failure then drives that call's own rollback, which is where finding (2) above reattaches: the losing call's rollback restores config.toml to whatever it looked like when *that* call started, with no check of what the winning call (or anything else) wrote to it in the meantime.

### 5. Taking ownership requires an explicit confirmation — PASS (mechanism is real; feature is unreachable)

`OwnershipTakeoverConfirmation(())` (`coexistence.rs:229-238`) has a private tuple field and the only public constructor is `user_explicitly_confirmed()`. **Tried to defeat it**: wrote a throwaway test (`crates/chimera-migration/tests/zzz_auditor_b_defeat_confirmation.rs`) attempting `OwnershipTakeoverConfirmation(())` directly from a separate test crate — compile error `E0423: cannot initialize a tuple struct which contains private fields`. This is a real, compile-time-enforced gate, not a runtime check a call site could forget; `take_ownership` (`coexistence.rs:244-261`) is unreachable without it, and `detect_coexistence` never calls `claim_ownership` on its own (`the_default_detection_path_never_calls_claim_ownership`, `tests/step7_4_coexistence.rs:303-335`, passes). Both temporary files were deleted after the test run.

Caveat that does not change the PASS but is worth stating plainly: this protection currently guards nothing reachable, because (per finding 4) nothing in the shipped app ever constructs a `CoexistenceVerdict::ConflictDetected` from real data to hand to `take_ownership` in the first place.

## What could not be verified

- **A real 1.x install or a real CC Switch install.** Neither `codex-plus-core`'s actual on-disk `settings.json` from a lived-in installation nor a real `~/.cc-switch/config.json` was available to test against. The CC Switch outer container shape (`apps.<type>.{providers,current}`) is explicitly flagged in the crate's own doc comment (`ccswitch_source.rs:11-14`) as "a best-effort reconstruction" that should be checked against a real install before wiring — this audit could not close that gap, only confirm the gap is honestly disclosed.
- **Real cross-process concurrency** (two actual OS processes, not a single-process reproduction via a test double's side effect). The reproduction above proves the code path has no defense by construction — the same logical proof the prior Task 5 audit used for `chimera-runtime`'s equivalent gap — but no multi-process stress test was run against a live filesystem across two real `chimera-desktop.exe` instances.
- **The real Windows process/ownership-manifest probe** that would back `CoexistencePort` in production. It does not exist yet (finding 4), so there is nothing concrete to test against a real "another manager is running" scenario, an MSIX-registered official install, or an external portable directory, as Step 7.5's real-machine coexistence matrix calls for.
- **Frontend accessibility/behavioral testing** of the new migration panel (added mid-audit at `6d854d0`) — no `npm test`/`npm run test:a11y` run was in scope for this Rust-focused audit; noted only by reading the source.
